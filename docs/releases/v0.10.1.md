# logwarden v0.10.1

**Status:** Planned

**Outcome: logwarden passes its own standard, and it's fast enough to check a large log
file in CI.** Two gaps found when we reviewed whether the tool is ready for production:

- logwarden's own messages were plain text on stderr, so logwarden failed its own standard. Checked
  with logwarden, two download messages gave two `adr_non_json_line` findings, a rule in the
  `essential` profile.
- A check took about 9 ms per log line (10,000 lines took 89 s), so a CI job with a large test
  log took minutes. About 7 ms of that went to logwarden's sensitive-data rules: Weaver's Rego
  engine runs each regular expression on every value.

## What's new

- **JSON messages: `LOGWARDEN_LOG_FORMAT=json`** (or `--log-format json`). Every message
  logwarden writes to stderr becomes one JSON record that passes the standard, even with the
  `standard` profile. This includes progress, warnings, errors, invalid arguments, a crash, and
  third-party library lines in `logwarden mcp`.
  - Each record has `timestamp`, `level`, a constant snake_case `event` (for example
    `weaver_download_started`, `logs_fetched`, `command_failed`), `logger`,
    `service.name=logwarden`, `service.version`, `deployment.environment.name` and
    `logwarden_detail`, which holds the same text as the plain-text message.
  - Warnings and errors add `error.type`. A crash adds `exception.type`, `exception.message` and
    `exception.stacktrace`.
  - The environment comes from `DEPLOYMENT_ENVIRONMENT` or `OTEL_RESOURCE_ATTRIBUTES`, as for
    `configure()`. Without either it is `production`.
  - `logwarden_detail` is declared in logwarden's registry, so a check of logs that include
    logwarden's own records needs no fields file.
  - The records go to stderr, not stdout: stdout carries the result (`--json`, the MCP
    protocol). Container platforms collect both.
- **The Docker image writes JSON messages by default.** Its output usually ends up in a log
  pipeline. The GitLab template sets `LOGWARDEN_LOG_FORMAT: text`, so job logs stay readable.
  Outside the image, plain text stays the default.
- **Faster checks.** Findings are the same as before; three changes make them cheaper:
  - Each sensitive-data rule first looks for text that any match must contain, such as `@` for
    an email address, `eyJ` for a JWT, or 13 digits in a row for a card number. The regular
    expression runs only when that text is present.
  - Each distinct field value (name, type, value) is checked once, and so is each distinct line
    shape (event, level, whether the trace context is valid, field names). Each line's findings
    are put back together from those results. Weaver judges every field on its own, and the
    per-line rules read only the shape, so the result is the same.
  - Large inputs are checked by several Weaver processes in parallel (up to 8), one chunk each.

## Changes you might notice

- With `-o DIR`, `samples.json` and `live_check.json` hold what Weaver was given: each distinct
  field and line shape once, not one sample per line.
- With the Docker image, messages on stderr are JSON unless you set
  `LOGWARDEN_LOG_FORMAT=text`. The wording and layout of messages are not part of the public
  interface (`STABILITY.md`), and the GitLab template keeps plain text.

## Breaking changes

None.
