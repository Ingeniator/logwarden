# logwarden v0.12.0

**Status:** Planned.

**Outcome: a go/no-go decision on metrics, backed by real services.** Logs and metrics have the
same problem: names and labels drift away from the standard. Before building a full metrics
workflow (planned as [v0.13.0](v0.13.0.md)), this version ships the smallest check that can
show whether logwarden finds problems in metrics that matter and that other tools miss. It runs
on the saved `/metrics` output of real services, and the result decides whether v0.13.0 starts.

No user has asked for metrics checks yet. Weaver already reports wrong names, units and
instrument types, and `promtool check metrics` reports Prometheus naming mistakes. What nothing
reports is the expensive part: labels with unbounded values, personal data in labels, and label
names that differ from the log fields. That is what this version has to prove useful.

## Spike results (2026-11-21)

Weaver v0.28 `live-check` with semconv 1.45, fed six metrics from the OTel Python SDK over
OTLP gRPC: one correct, five with typical mistakes
([`tests/data/metrics_spike/emit.py`](https://github.com/Ingeniator/logwarden/blob/main/tests/data/metrics_spike/emit.py)).

| Mistake | Found by | Finding |
|---|---|---|
| Custom name where semconv has one (`api_latency_ms`) | Weaver | `missing_metric` (no hint to the semconv name) |
| Semconv metric with unit `ms` instead of `s` | Weaver | `unit_mismatch` |
| Duration as a counter instead of a histogram | Weaver | `unexpected_instrument` |
| Label `status` | logwarden Rego, unchanged | `adr_banned_synonym` |
| Email address in a label value | logwarden Rego, unchanged | `adr_sensitive_data` (message says "don't log it") |
| 300 distinct `user.id` values on one counter | nothing | `user.id` is valid semconv, so nothing flags it |
| `payments_total_count` (suffixes in the name) | Weaver, partly | only `missing_metric`, no naming hint |
| Missing resource attributes | nothing | resources aren't checked |

Also found:
- Weaver accepts metric samples from a JSON file (`--input-source file`), the way logwarden
  already feeds it logs. Scraped Prometheus text can be converted to samples, with no OTLP
  listener needed.
- Weaver's OTLP listener is gRPC only; `logwarden capture` is OTLP/HTTP.
- One finding per data point: 300 series gave 300 identical findings. Findings need grouping
  per metric and attribute.

So the existing pipeline carries over. New work: input conversion, cardinality, resource
checks, naming hints and grouping.

## What's new

- **`logwarden check --signal metrics` (experimental)** on Prometheus or OpenMetrics text, such
  as a saved `curl :8000/metrics`.
  - Prometheus names are translated back to OTel names for Weaver
    (`http_server_request_duration_seconds` → `http.server.request.duration`, unit `s`; `_total`,
    `_ratio` and unit suffixes per the OTel compatibility spec). Dotted UTF-8 names from
    Prometheus 3 are read as they are. `# TYPE` gives the instrument.
  - Weaver's findings (`missing_metric`, `unit_mismatch`, `unexpected_instrument`,
    `required_attribute_not_present`) get hints and `docs/rules.md` entries.
  - The label rules run on metric labels unchanged: `adr_banned_synonym`,
    `adr_semconv_prefix`, `adr_sensitive_data`.
  - New rule `adr_metric_cardinality`: a label from the unbounded list (IDs, emails,
    `url.full`, `url.path`, …), or a metric over its series budget (default 1,000 per metric).
  - **One finding per metric and label,** with the number of series, instead of one per series.
  - When semconv has a metric for a custom one, `missing_metric` names it and its Prometheus
    name (`http_requests_total` → `http.server.request.duration`, exported as
    `http_server_request_duration_seconds`; LLM token counters → the GenAI semconv token
    metrics). Without that hint, `missing_metric` was the one finding the spike rated not useful.
  - Domain metrics are declared in the fields file, as a Weaver group with `type: metric`
    (moved forward from v0.13.0: it needed no new code).
  - Not checked: the metrics client libraries export on their own (`process_*`, `python_*`,
    `go_*`, `jvm_*`, `nodejs_*`, `promhttp_*`) and the `_created` series of `prometheus_client`.
    A label value is typed as the registry types the attribute (`"200"` → `200` for
    `http.response.status_code`), since Prometheus labels are always text.
  - `--series-budget N` sets the budget for all metrics (per metric is v0.13.0). The config's
    `fields` and `disable` apply, and `disable` accepts the metric rule ids.
  - Outputs: the text summary, `--json` and `--markdown`. Exit codes as for logs. Options that
    are logs only for now (`--baseline`, `--compare`, `--sarif`, `--codequality`, `--html`,
    `--snapshot`, `--metrics`, `-o`) exit 2 with a message.
  - Experimental: rule ids, messages and options for metrics may still change, unlike those for
    logs. The help and docs say so.
- **The trial** (the point of this version). The check runs on the `/metrics` output of
  five real services: `aihub`, `databridge`, `yallmp-sync`, `clickstream` and `meta-evaluator`
  (ai-suite), and of the GitLab team's services if they agree. `promtool check metrics` runs on
  the same files. Each finding is reviewed with the service's owner and marked *worth fixing*
  or *not*. The results go into a table in these notes, with no metric values or label values.

## Trial results (2026-11-24)

The `/metrics` output of the five services, collected without their production dependencies:
the `prometheus_client` registry written at the end of the test run (aihub, databridge,
yallmp-sync), or the service run locally and `/metrics` fetched after a few requests
(clickstream, with a stub for its database; meta-evaluator). Library metrics (`process_*`,
`python_*`, `_created`) are not counted. The owner marked the findings by kind.

| Service | Metrics / series | Findings | by rule | Only logwarden¹ | `promtool` | Not worth fixing |
|---|---|---|---|---|---|---|
| aihub | 6 / 99 | 19 | banned synonym 8, missing metric 6 (5 with a semconv hint), missing attribute 5 | 13 | 0 | 0 |
| databridge | 17 / 71 | 25 | missing metric 17 (2 with a hint), missing attribute 4, banned synonym 3, cardinality 1 | 6 | 0 | 0 |
| yallmp-sync | 11 / 103 | 49 | missing attribute 21, missing metric 11 (5 with a hint), banned synonym 9, cardinality 8 | 22 | 0 | 0 |
| clickstream | 5 / 8 | 10 | missing metric 5 (2 with a hint), banned synonym 3, missing attribute 2 | 5 | 0 | 0 |
| meta-evaluator | 5 / 5 | 6 | missing metric 5, deprecated 1 | 0 | 1² | 1³ |
| **Total** | 44 / 286 | **109** | | **46** | **1** | **1 (0.9%)** |

¹ Not reported usefully by Weaver alone or `promtool`: logwarden's label rules
(`adr_banned_synonym`), `adr_metric_cardinality`, and `missing_metric` with a semconv hint.
² A gauge named `…_total`; logwarden reports only `missing_metric` for it.
³ A label `state` reported as `deprecated` (semconv renamed an old `state` attribute to
`db.client.connection.state`): noise for a domain metric's own label.

What was found, by kind (all marked worth fixing by the owner):
- Four services export their own HTTP metrics with the labels `method`, `status` /
  `status_code` and `handler` / `endpoint` instead of semconv's `http.server.request.duration`
  with `http.request.method`, `http.response.status_code` and `http.route`: the same names that
  differ between their logs and metrics.
- yallmp-sync: `model` instead of `gen_ai.request.model` on its LLM metrics; token counters
  that GenAI semconv defines; `group_id` on 8 metrics, and in databridge `org_id`, flagged as
  unbounded.
- Domain metrics and labels that no registry declares (all five services).

## Decision: go

- In 4 of 5 services (aihub, databridge, yallmp-sync, clickstream) logwarden found problems
  the owner agrees are worth fixing and that neither `promtool` (one finding in all five) nor
  Weaver alone reports usefully. Required: 3 of 5.
- 1 of 109 findings (0.9%) is not worth fixing. Allowed: 30%.

[v0.13.0](v0.13.0.md) starts. From the trial: a fields-file workflow for domain metrics
(most findings are undeclared domain metrics and labels), `deprecated` not reported on a
domain metric's own unprefixed label, and promtool's naming checks (`_total` on a gauge) as
part of `adr_metric_name`.

## Decision rule

**Go** (v0.13.0 starts, re-scoped by what the trial found) if both hold:
- in at least 3 of the 5 services, logwarden finds at least one problem the owner agrees is
  worth fixing **and** that neither `promtool` nor Weaver alone reports usefully (a raw
  `missing_metric` without a hint counts as not useful);
- at most 30% of all findings are judged not worth fixing.

**No-go** otherwise: v0.13.0 is dropped from the roadmap, `--signal metrics` stays
experimental (or is removed in the next release if it found nothing), and the metrics standard
stays a document for code review.

## Not in this version

Everything that only matters once metrics checks are known to be useful moves to v0.13.0:
OTLP input and `capture /v1/metrics`, naming rules (`adr_metric_name`), resource checks,
required metrics, per-metric series budgets, baseline and `--compare`, SARIF, Code Quality,
HTML, the GitLab template, the Action and MCP.

## Bug fixes

- `logwarden check` on an empty log file, or one with only blank lines, crashed with
  `ValueError: range() arg 3 must not be zero` (exit 1) instead of reporting
  `0 records, 0 violations`. A test run that writes no log lines now passes the check with 0
  records; services no longer need to log a startup line to keep CI from crashing. The same
  for stdin and `baseline`.

## Breaking changes

None. Nothing changes for logs, except the empty-file crash above.
