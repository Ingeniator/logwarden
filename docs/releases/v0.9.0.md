# logwarden v0.9.0

**Status:** Planned.

Check production logs on a schedule. v0.8.0 already reads Elasticsearch `_search` responses
and writes per-service metrics. v0.9.0 adds the missing parts: a scheduled job that exports the
last hour from Elasticsearch and checks it, pushes the metrics to Prometheus, and keeps a trend
in Grafana. Nothing runs permanently and nothing reads Kafka: it's a CI job like the others.

`logwarden watch`, a long-running consumer of the live stream, was planned here first. It was
dropped (2026-11-22): the only team using logwarden runs it in CI only, with no shared state,
and an hourly job gives the same view without a service to deploy, operate and authenticate
to Kafka. It is listed under "Later" in the roadmap, in case a user needs minutes of delay
instead of an hour.

## What's new

- **Scheduled check of production logs.** A second hidden job in the GitLab template,
  `.logwarden-production`, for a scheduled pipeline (and the same steps as a shell recipe for
  cron or a Kubernetes CronJob):
  - It queries Elasticsearch for the last `LOGWARDEN_SINCE` (default `1h`) of
    `LOGWARDEN_ES_INDEX`, up to `LOGWARDEN_ES_SIZE` hits (default 10,000, Elasticsearch's
    default limit), with credentials from a CI variable (`LOGWARDEN_ES_AUTH`, API key or basic).
    The hits are a sample of the hour, and the report says so.
  - It runs `check` on the response with `[source]` from the project's config, and writes the
    Markdown and HTML reports and the snapshot as artifacts.
  - It compares with the previous scheduled run's snapshot: new and fixed findings since the
    last hour.
  - With `LOGWARDEN_PUSHGATEWAY` set, it pushes the `--metrics` output to a Prometheus
    Pushgateway (one group per job, replaced on each push).
  - It never fails on violations (they are the finding, not an error). It fails on a bad
    config, an unreachable Elasticsearch or an empty result, so a broken schedule is noticed.
  - The job uses the image and works without internet access, like the merge-request job.
- **Grafana dashboard** `integrations/grafana/logwarden.json`: share of lines with violations
  per service, violations by rule, and the time of the last push (a stale schedule shows).
  The panels use the values of the last push, not `rate()`, because each push is one window.
- **Pinned Weaver and semconv versions stay current.** A weekly workflow, `update-pins.yml`,
  looks for new releases. When it finds one, it updates the version and its SHA-256, runs the
  tests, and opens a PR. This keeps the project maintained with less manual work.

## Fixes and maintenance

- **Archive paths on Windows.** On Python 3.10 and 3.11 the downloaded Weaver and semconv
  archives are checked member by member. A name such as `/x` or `C:/x` wasn't seen as absolute
  on Windows. Every name is now checked with Windows path rules on every OS. The archives were
  already checked against a pinned SHA-256, so no download could have used this.
- **Test coverage is measured in CI** (job `coverage`), including the CLI and MCP server that
  tests start as subprocesses. Below 85% the job fails. 93% at the time of writing.

## Breaking changes

None expected.
