# logwarden v0.9.0

**Status:** Planned.

Check the live log stream continuously. v0.8.0 analyses exports; `logwarden watch` reads the
stream itself, from the Kafka topic Fluent Bit writes to, and publishes the per-service
metrics from v0.8.0 to Prometheus and the findings to Kibana.

## What's new

- **`logwarden watch`: a long-running check of the live log stream.**

  ```bash
  logwarden watch --from kafka://kafka:9092/app-logs     # read the topic Fluent Bit writes to
  logwarden watch --from http://0.0.0.0:8686              # Fluent Bit http output
  logwarden watch --from otlp://0.0.0.0:4318              # OTel SDKs or a Collector
  kubectl logs -f deploy/api | logwarden watch --from -   # anything else, on stdin
  ```

  - **Kafka (the main source).** `watch` joins its own consumer group (`logwarden` by
    default) and starts from the latest offset. It only reads: Fluent Bit, Elasticsearch and
    other consumers aren't affected, and nothing in the pipeline has to change. SASL and TLS
    settings are passed through with `--kafka-option security.protocol=SASL_SSL` and similar.
    The Kafka client is the optional extra `logwarden[kafka]` (confluent-kafka). The Docker
    image includes it.
  - **HTTP.** Accepts what the Fluent Bit `http` output sends (`format json_lines` or
    `json`), with no extra install. This suits setups without Kafka, such as a local
    docker-compose.
  - **OTLP.** The same receiver as `capture`.
  - Records are unwrapped with the `[source]` section from v0.8.0.
  - **Checks in windows.** Lines are collected for `--window` (default 60s) and checked
    together, grouped by service. Memory is bounded: past `--max-lines` (default 50,000)
    per window, lines are counted but not checked, and `--sample 0.1` checks a fraction of
    the lines on a busy topic. Throughput is measured and stated in the docs.
  - **Outputs.**
    - Prometheus metrics on `--metrics-port` (default 9464). These are the v0.8.0 per-service
      metrics, kept as running counters, plus `logwarden_lines_skipped_total{service}` and
      `logwarden_source_up`. Labels are bounded: rule ids are a fixed list, and services past
      `--max-services` (default 200) are counted as `other`.
    - Findings as JSON lines on stdout, following the standard themselves
      (`event: "logwarden_finding"` with the rule, field, logger, the event that was checked,
      the service and a count). Each finding is written once per window, with a count. When
      `watch` runs in the cluster, Fluent Bit ships these lines to Kafka and Elasticsearch
      like any other container's output. Use
      `--findings-to kafka://kafka:9092/logwarden-findings` to send them to a topic instead.
    - `--snapshot FILE`, rewritten after each window, and `--catalog FILE`, which merges the
      event names seen in production into the event catalog.
    - `/healthz`.
  - Findings never contain logged values. `watch` doesn't fail on violations. It exits 2 on a
    bad config. When the source is unreachable it keeps retrying with backoff and sets
    `logwarden_source_up 0`.
  - **Dashboards and a demo.**
    - `integrations/grafana/logwarden.json`: compliance and violations by service and rule.
    - `integrations/kibana/logwarden.ndjson`: saved objects for `logwarden_finding` lines.
    - `integrations/kafka-demo/`: a docker-compose with Kafka, Fluent Bit and `watch`, plus
      Elasticsearch and Kibana in an optional profile.
- **Pinned Weaver and semconv versions stay current.** A weekly workflow, `update-pins.yml`,
  looks for new releases. When it finds one, it updates the version and its SHA-256, runs the
  tests, and opens a PR.

## Breaking changes

None expected.
