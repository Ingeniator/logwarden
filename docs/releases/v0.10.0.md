# logwarden v0.10.0

**Status:** Planned.

**Outcome: a team on the `essential` profile moves to the full standard in one reviewed
change, without a wall of findings.** After v0.9.0 a team starts with the rules every service
should pass. The next step, `standard`, adds the naming rules, and on an existing service most
of its findings are `missing_attribute`: custom fields the registry doesn't know yet. This
version turns them into a fields file to review instead of hundreds of findings to read, and
keeps the pinned Weaver and semconv versions current without manual work.

## What's new

- **`logwarden init --from LOGS`** reads real logs (any input `check` accepts, including
  Elasticsearch and Kibana exports) and writes `logwarden-fields.yaml` with every custom field it
  saw, its type and how many lines had it.
  - Fields that are synonyms of semconv names (`status`, `user_id`, …) or look sensitive are
    *not* declared. They are listed in a comment at the top of the file with the rule that
    reports them, so they still get fixed rather than accepted.
  - Fields written with underscores where semconv has a dotted name aren't declared either
    (`adr_semconv_prefix`).
  - Running it again on newer logs adds new fields and keeps the existing entries and their
    edits.
  - `init --from` also sets `profile = "standard"` in the config, so the change that adds the
    fields file is the change that turns on the full standard.
- **"Ready for standard" in the summary.** Under `essential`, the summary says how many of the
  findings `standard` would add are unknown fields that `init --from` would declare, and how
  many are other rules: how big the move is, before making it.
- **Pinned Weaver and semconv versions stay current.** A weekly workflow, `update-pins.yml`,
  looks for new releases. When it finds one, it updates the version and its SHA-256, runs the
  tests, and opens a PR. This keeps the project maintained with less manual work.
