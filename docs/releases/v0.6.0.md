# logwarden v0.6.0

**Status:** Planned. Notes written before implementation; each claim is checked below
before release.

Any language: check services written in Node, Go, Java or anything with an OpenTelemetry
SDK, run logwarden without Python, and catch problems in source before anything runs.

## What's new

- **`logwarden capture`: receive logs over OTLP.** A small OTLP/HTTP receiver (port 4318,
  protobuf and JSON encodings, no extra dependencies). Each OTLP log record becomes one line
  in the standard's shape: resource attributes (`service.name`, …) merged in, `event` from
  the record's event name or string body, `level` from the severity, `logger` from the
  instrumentation scope, W3C `trace_id`/`span_id`, attributes as fields. The lines go
  through the same `check` (baseline, `disable`, `upstreams` all apply).

  ```bash
  logwarden capture -o logs.jsonl -- npm test     # runs the command with OTEL_* pointing at the receiver, then checks
  logwarden capture -o logs.jsonl                  # or receive until Ctrl-C / SIGTERM
  ```

  With a command, it listens on a free port, sets `OTEL_EXPORTER_OTLP_ENDPOINT`,
  `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` (an existing `http/json` is kept) and
  `OTEL_LOGS_EXPORTER=otlp`, runs it, then runs `check` on what arrived. The exit code is
  the command's if it failed, otherwise the check's; no records at all is a setup error
  (exit 2). The command's stdout goes to stderr, so `--json` stays parseable. Requests may
  be gzip/deflate-compressed or chunked; traces and metrics sent to the same endpoint are
  accepted and ignored. Attributes with an empty OTLP value are left out, and a non-string
  body next to an event name goes to `log.record.original`. `--host 0.0.0.0` for containers.
  (The roadmap said Weaver's live-check receiver. Weaver judges OTLP records directly but
  returns no lines, so the baseline, line numbers and upstream coverage wouldn't work there.
  gRPC isn't supported; SDKs default to it in some languages, so set the protocol to
  `http/protobuf`, which `capture -- cmd` does.)
- **Docker image** `ghcr.io/ingeniator/logwarden:0.6.0` (and `:latest`), linux/amd64 and
  linux/arm64, with Weaver and the semantic conventions inside, so it works offline:

  ```bash
  docker run --rm -v "$PWD:/work" ghcr.io/ingeniator/logwarden:0.6.0 check logs.jsonl
  ```

  It runs as any user (`--user $(id -u)`), with the cache read-only.
- **Setup recipes** for Node (pino), Go (`log/slog`) and Java (logback +
  logstash-logback-encoder) in `docs/recipes/`, each with a runnable example in
  `examples/recipes/` whose output passes the check. The Node recipe also shows the
  OTLP route through `logwarden capture`.
- **Source checks: `logwarden lint-code [PATHS]`** runs [Semgrep](https://semgrep.dev) with
  logwarden's rules (`_data/semgrep/logwarden.yml`) for Python, JavaScript/TypeScript, Go
  and Java. Semgrep needs one rule per language, so each check has four ids with a
  `-python`, `-js`, `-go` or `-java` suffix (16 rules):
  - `logwarden-event-name-*` (§4): a formatted log message (f-string, `%`, `.format`, `+`,
    template literal, `fmt.Sprintf`, `String.format`) or a literal one that isn't
    snake_case (`"Imported rows"`, SLF4J `"Imported {} rows"`), as the runtime
    `adr_event_name` rule would report it.
  - `logwarden-sensitive-key-*` (§8): a field named like `password`/`token`/`api_key`.
  - `logwarden-banned-key-*` (§2): a banned synonym as a field name (same list as the
    runtime rule).
  - `logwarden-print-*` (§1, warning): `print` to stdout, `console.log`, `fmt.Println`,
    `System.out.println`, `printStackTrace()` instead of the logger; test files, `scripts/`,
    `cmd/` and `cli.py` are skipped.

  `--json`, `--exclude-rule ID` (repeatable) and `--list`. Semgrep isn't a dependency: it
  pins old OpenTelemetry and `mcp` versions that would clash with a project's (and with
  `logwarden[mcp]`), so there is no `[lint]` extra. `lint-code` uses `semgrep` from `PATH`,
  or runs a pinned Semgrep with `uvx` when uv is installed. Semgrep doesn't run natively on
  Windows. Like Semgrep, it skips `tests/` directories. Exit codes as for `check`: 0 clean,
  1 findings, 2 setup error.

## Fixes

- **A read-only cache broke every check.** `logwarden` made the cached Weaver binary
  executable on each run, which fails when the cache belongs to another user (found by
  running the Docker image as non-root). It now only does so when needed.
- `logwarden setup` also downloads the semantic conventions, so a machine (or image) can be
  prepared for offline use in one step.

## Breaking changes

None. The core install still has no dependencies besides `tomli` on Python 3.10.

## Upgrading from v0.5.0

Nothing to change. For other languages, follow `docs/recipes/`, then either write JSON
lines to a file and run `check`, or wrap the test command in `logwarden capture -- ...`.
CI: `uses: Ingeniator/logwarden@v0.6.0`, or the Docker image.
