# logwarden v0.10.2

**Status:** Planned

**Outcome: a field logged as a list passes when it's declared as a list.** Reported by a user:
a field declared `type: string[]` in `logwarden-fields.yaml`, logged as `["a","b"]`, failed
with `type_mismatch` ("Attribute 'tags' has type 'string'. Type should be 'string[]'."), so no
list field could pass. logwarden gave Weaver every list as JSON text, typed `string`. For the
same reason `logwarden init --from` proposed `type: string` for list fields.

## Fixes

- **Lists are checked as arrays.** A list whose items are all one type goes to Weaver as
  `string[]`, `int[]`, `double[]` or `boolean[]`, with its items. Ints and doubles together are
  `double[]`. A list with mixed items, nulls, lists or objects is still checked as JSON text
  (`string`), as before. This also applies to semconv fields typed as arrays, such as
  `process.command_args`.
- **An empty list takes the declared type.** `[]` has no items to go by, so when the field is
  declared as an array type, it is checked as that type. Otherwise it stays JSON text. This
  costs one extra Weaver call (resolving the registry), only when the input has an empty list.
- **Secrets inside lists are still found.** The sensitive-data rules scanned a list's JSON text.
  They now scan each item (strings and whole numbers), one item at a time, so two numbers never
  join into a card number.
- **`init --from` proposes array types**, e.g. `type: string[]` for a list of strings. Empty
  lists don't count when picking the type; a field that was only ever `[]` is `string[]`.

## Changes you might notice

- A list field that was declared `string` to get past the bug now fails with `type_mismatch`.
  Change it to the array type.
- A list field in the `essential` profile: no change (unknown and mistyped fields are outside
  `essential`).

## Breaking changes

None.
