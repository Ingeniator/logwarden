# logwarden v0.10.2

**Status:** Released 2026-11-23 · tag v0.10.2

**Outcome: fixes for bugs found by a user.** Following the standard could still fail the check, or lose information:

1. **Lists.** A field declared `type: string[]` in `logwarden-fields.yaml`, logged as
   `["a","b"]`, failed with `type_mismatch` ("Attribute 'tags' has type 'string'. Type should
   be 'string[]'."), so no list field could pass. logwarden gave Weaver every list as JSON text,
   typed `string`. For the same reason `logwarden init --from` proposed `type: string` for list
   fields.
2. **`gen_ai.*` fields.** The standard (§2) says to log `gen_ai.provider.name`,
   `gen_ai.request.model` and `gen_ai.usage.input_tokens`, and `adr_banned_synonym` suggests
   `gen_ai.request.model` for `model`. But each of them failed with `deprecated` ("Moved to the
   OpenTelemetry GenAI semantic conventions repository"). In semantic conventions 1.45.0, which
   logwarden bundles, every GenAI field is deprecated because it moved to a separate
   repository, not because it was renamed, so the finding names nothing to use instead. A
   service that calls an LLM could not pass the `standard` profile.
3. **Source lines missing when logging is set up in `conftest.py`.** The pytest plugin turns on
   `code.file.path` and `code.line.number` (for `--sarif`, GitLab Code Quality and "Fix
   first" by file and line) by setting `LOGWARDEN_CALLSITE=1` in `pytest_configure`. pytest
   imports `conftest.py` before that, so a `configure()` at the top of `conftest.py` ran
   without it: 0 of 106 captured lines had the fields in one service, while another, which set
   up logging later during test collection, had them on 569 of 569.
4. **`init --from` contradicted the standard on naming.** Its comment on a field without dots
   said "A bare name: better namespaced (e.g. myservice.auth_source) in the code", while
   §2 says a service's own fields are snake_case without dots.
5. **Timestamp ids reported as card numbers.** `adr_sensitive_data` took any 13 to 19 digits
   starting with 2 to 6, with a space or dash anywhere, that pass the Luhn checksum, so about one
   id in ten like `20260911-120000` or `ui_draft/20261122-155637-…` was "a card number".
6. **A baseline entry hid every secret in its field.** A baseline entry matches by rule, field,
   logger and event. The workaround for 5 (baselining `query_params` on `Request completed`)
   also hid a real JWT planted in that field on a later line.
7. **Python 3.10 and 3.11 couldn't unpack the GenAI archive** (found by CI on this release). The
   archive has two symlinks (`CLAUDE.md -> AGENTS.md`), and without Python 3.12's extraction
   filters logwarden rejected any archive with a link: "unsafe path in archive".

## Fixes

### Lists

- **Lists are checked as arrays.** A list whose items are all one type goes to Weaver as
  `string[]`, `int[]`, `double[]` or `boolean[]`, with its items. Ints and doubles together are
  `double[]`. A list with mixed items, nulls, lists or objects is still checked as JSON text
  (`string`), as before. This also applies to semconv fields typed as arrays, such as
  `process.command_args`.
- **An empty list takes the declared type.** `[]` has no items to go by, so when the field is
  declared as an array type, it is checked as that type. Otherwise it stays JSON text. This
  costs one extra Weaver call (resolving the registry), only when the input has an empty list.
- **Secrets inside lists are still found.** The sensitive-data rules scanned a list's JSON text.
  They now scan each item (strings and whole numbers), one item at a time, so two numbers never
  join into a card number.
- **`init --from` proposes array types**, e.g. `type: string[]` for a list of strings. Empty
  lists don't count when picking the type; a field that was only ever `[]` is `string[]`.

### GenAI fields

- **logwarden bundles the [OpenTelemetry GenAI semantic
  conventions](https://github.com/open-telemetry/semantic-conventions-genai) v0.1.0** (their
  first release, built on semantic conventions 1.45.0) next to semantic conventions 1.45.0.
  The `gen_ai.*`, `openai.*`, `mcp.*`, `a2a.*` and `aws.bedrock.*` fields they define are
  current fields again, with GenAI's types (for example `gen_ai.request.top_k` is now `int`).
- **Each field has one definition.** Semantic conventions 1.45.0 keeps the moved fields as
  deprecated in its `gen-ai`, `mcp` and `openai` directories. With both registries loaded, Weaver
  reports each such field as declared twice and uses one definition or the other depending on
  the group order, so `gen_ai.tool.name` and the `mcp.*` fields stayed deprecated. logwarden
  leaves out the semconv directories that GenAI replaces (those with the same name).
- **Old GenAI names still say what to use.** Names that GenAI v0.1.0 no longer has would
  otherwise be reported as unknown (`missing_attribute`). logwarden's registry declares them as
  deprecated, with the new name: `gen_ai.system` → `gen_ai.provider.name`,
  `gen_ai.usage.prompt_tokens` → `gen_ai.usage.input_tokens`, `gen_ai.usage.completion_tokens` →
  `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_creation.input_tokens` →
  `gen_ai.usage.cache_write.input_tokens`, `gen_ai.workflow.name` → `gen_ai.agent.name`,
  `gen_ai.openai.request.seed` → `gen_ai.request.seed`, `gen_ai.openai.request.response_format` →
  `gen_ai.output.type`, the three `gen_ai.openai.*` service tier and fingerprint fields →
  `openai.*`. `gen_ai.token.type` is deprecated without a new name (GenAI replaced it with
  separate histograms).
- **Offline:** the GenAI archive is downloaded once with a pinned SHA-256 and cached, like the
  semantic conventions; `logwarden setup` and the Docker image include it. To use your own copy,
  set `LOGWARDEN_SEMCONV_GENAI` to its `model` directory (new environment variable).
- **The pin update** (`update-pins.yml`) also looks for new GenAI releases.
- `docs/standard.md`: the GenAI note now says logwarden bundles the GenAI conventions, and
  that `deprecated` findings name the new field when there is one.

### Secret findings

- **Card numbers need an issuer's prefix and length** (Visa 13/16/19 digits, Mastercard 51-55
  and 2221-2720, American Express 34/37, Diners Club, Discover, JCB, UnionPay, Maestro) and
  card grouping: no separators, groups of 4 (`4111 1111 1111 1111`, with a last group of up to
  3), or 4-6-5 / 4-6-4 (American Express, Diners Club). Then the Luhn checksum, as before.
  `20260911-120000` (14 digits starting 2026, 8-6 grouping) is neither.
- **Baseline entries for `adr_sensitive_data` record what was found:** a new `kind` key
  (`key`, `nested`, `jwt`, `bearer_token`, `api_key`, `private_key`, `url_credentials`,
  `email`, `card_number`). An entry hides only that kind, so a known card number in a field no
  longer hides a JWT there. Entries of other rules are unchanged. `--compare` with a snapshot
  matches the same way, and the SARIF and Code Quality fingerprints of secret findings include
  the kind.
- **Old secret entries hide nothing.** A baseline written before v0.10.2 has no `kind` on its
  `adr_sensitive_data` entries, so it can't say which secret it accepted. Those entries no
  longer match. The result counts them in a new `--json` key, `baseline_outdated`, and the text
  and Markdown output say: "N adr_sensitive_data entries are from before v0.10.2 and no longer
  hide anything; check those findings, then run 'logwarden baseline'". They are not counted in
  `baseline_fixed`.

### Other fixes

- **The pytest plugin sets `LOGWARDEN_CALLSITE=1` when it is imported** (only while
  `LOGWARDEN_CAPTURE` is set, and not over a value you set). pytest imports plugins installed
  with the package before any `conftest.py`, so logging set up there gets the source fields.
- **Archives unpack on Python 3.10 and 3.11:** links in a downloaded archive are skipped
  instead of failing the download (nothing logwarden reads is a link). Absolute paths and `..`
  are still refused. Python 3.12 and later already used the safe extraction filter.
- **`init --from` follows the standard:** the hint is now on dotted names ("Dotted: the
  standard (§2) names a service's own fields snake_case without dots; dots are for semconv
  names"), and fields without dots get none. The Claude Code skill says the same.

## Changes you might notice

- A list field that was declared `string` to get past the bug now fails with `type_mismatch`.
  Change it to the array type.
- GenAI fields: `deprecated` findings on current GenAI fields go away. A field that GenAI
  changed can now fail where it passed: `gen_ai.request.top_k` logged as a decimal
  (`type_mismatch`, now `int`), and fields GenAI removed or renamed (`deprecated` with the new
  name). Fields from other semconv areas are unchanged.
- A list field in the `essential` profile: no change (unknown and mistyped fields are outside
  `essential`).

- Fewer `adr_sensitive_data` findings for numbers that only looked like cards: ids and
  timestamps with dashes in non-card places, and digit strings with no card issuer's prefix
  and length. On the five sample sets (below) no finding changed.
- GitHub code scanning and GitLab Code Quality show existing secret findings once as fixed and
  new, because their fingerprint now includes the kind.

## Breaking changes

- **A baseline with `adr_sensitive_data` entries fails again** until it is regenerated: check
  the findings it now reports (`baseline_outdated` says how many entries are affected), fix
  the real ones, then run `logwarden baseline`. This breaks the promise that a baseline from
  an older version keeps working, under the security exception now in `STABILITY.md`: an old
  entry can't tell an accepted value from a leaked secret.
