# logwarden v0.4.0

**Status:** Planned. Notes written before implementation; each claim is checked below
before release.

Safe to adopt on an existing service: record what's there today, fail only on new
problems, and switch off a rule with a written reason. Three new rules cover secrets and
personal data, lines that aren't JSON, and malformed trace context.

## What's new

- **Baseline.** `logwarden baseline logs.jsonl` writes `.logwarden-baseline.json` with the
  current findings. When a baseline is configured (`baseline = ".logwarden-baseline.json"`),
  `check` fails only on findings that aren't in it. Findings are matched by rule, field,
  logger and event name with numbers and ids masked, not by line number, so they survive
  code moving around. `check --baseline FILE` and `--no-baseline` override the config.
  The result reports how many findings the baseline hid and how many baseline entries no
  longer occur (fixed), so the baseline can be shrunk.
- **Disable a rule, with a reason.** `disable = { adr_event_name = "legacy events, see JIRA-123" }`.
  An empty reason, an unknown rule id or the list form `disable = ["..."]` is an error
  (exit 2). Disabled rules and their reasons are listed in every result, so they stay
  visible.
- **New rule `adr_sensitive_data` (§8).** Fails on:
  - field names such as `password`, `secret`, `api_key`, `authorization`, `cookie`,
    `*_token` (also inside nested objects), unless the value is redacted (`***`, `[REDACTED]`, …);
  - values that look like a JWT, a `Bearer` token, a known API-key format (OpenAI/Anthropic
    `sk-`, GitHub, GitLab, AWS `AKIA`, Slack, Google `AIza`), a private-key block,
    credentials in a URL (`scheme://user:pass@`), an email address, or a card number
    (checked with the Luhn checksum).

  The message names the field and the kind of data, never the value itself, so findings
  are safe to print in CI.
- **New rule `adr_non_json_line` (§1).** A line that isn't a JSON object (a plain-text
  banner, a traceback printed by a library, a JSON array) is a violation. Blank lines are
  still ignored. Before, such lines were only counted in `skipped_lines`.
- **New rule `adr_trace_context` (§3, §7).** `trace_id` must be 32 lowercase hex characters
  and `span_id` 16, not all zeros (the W3C format), and `span_id` needs a `trace_id`.
- **Source linters in the agent instructions.** The skill and the `AGENTS.md` snippet tell
  agents to run Ruff `LOG`/`G`/`TRY400` (Python) or sloglint (Go) when the project uses them,
  and never to silence findings by adding them to the baseline or `disable` unless asked.

## Fixes

- A line whose `event`, `trace_id` or `span_id` is not a string (a number, an object, …)
  made Weaver reject the whole input, so `check` failed with exit 2 for every line. Such
  values are now converted to strings and reported by the rules (`adr_event_name`,
  `adr_trace_context`).
- `adr_failure_context` cited §12, the section number in the old ai-suite ADR. It now cites
  §10 of the canonical standard. The rule id is unchanged.

## Breaking changes

- Lines that aren't JSON objects now fail the check (`adr_non_json_line`) instead of only
  being counted. If the input mixes in output that isn't the service's logs, capture only
  the service's output, or set `disable = { adr_non_json_line = "<reason>" }`.
- Logs that contain the patterns above now fail `adr_sensitive_data`.
- `--json` gains keys (`baselined`, `baseline`, `baseline_fixed`, `disabled`); existing keys
  keep their meaning. When a baseline or `disable` applies, `violations`, `by_rule` and
  `findings` count only the findings that still fail.

## Upgrading from v0.3.0

```bash
uv add --dev logwarden@0.4.0        # CI: uses: Ingeniator/logwarden@v0.4.0
logwarden check logs.jsonl          # new rules may report findings
# To adopt gradually on an existing service:
logwarden baseline logs.jsonl       # writes .logwarden-baseline.json; commit it
# pyproject.toml
# [tool.logwarden]
# baseline = ".logwarden-baseline.json"
```

Claude Code: `/plugin update logwarden@logwarden`.
