# logwarden v0.8.0

**Status:** Planned.

Findings on the source line, and analysis of the logs already in Kibana. SARIF puts each
finding on the `log.info(...)` call in the PR diff. `check` reads Kibana and Elasticsearch
exports directly, unwraps what Fluent Bit added to each record, and breaks the result down
by service.

## What's new

- **Findings on the source line: SARIF.**
  - `lint-code --sarif FILE` writes Semgrep's findings as SARIF 2.1.0.
  - `check --sarif FILE` does the same for runtime findings, when log lines say where they were
    logged: `code.file.path`, `code.line.number` and `code.function.name` (semconv 1.45).
    `logwarden.logging.configure(callsite=True)` adds these fields, and the pytest plugin turns
    this on during tests. The Go recipe gets them from slog's `AddSource`. A finding without a
    location is attached to its line in the log file, so it isn't lost. `--source-root`
    removes a path prefix, so locations match the repository.
  - Each SARIF rule links to its section of `docs/rules.md` at this version.
  - The GitHub Action gets a new input, `sarif: "true"` (default `"false"`). It uploads the
    check's SARIF with `github/codeql-action/upload-sarif`, which needs
    `security-events: write`; without it, the upload warns and the check still decides the
    job. Code scanning then shows each finding on the log call in the PR diff. Code scanning
    is available on public repositories, and on private ones with GitHub Advanced Security.
    The Action doesn't run `lint-code`; `docs/integration.md` shows the two steps that upload
    its SARIF.
- **Kibana and Elasticsearch exports as input.** `check`, `baseline`, `catalog` and
  `--snapshot`/`--compare` accept these exports as well as JSON lines. The format is detected
  automatically, or set with `--format`:
  - `csv`: a Kibana Discover CSV report. Each row is one record, and each column is a field.
    - When a `_source`, `log` or `message` column holds the whole JSON line, that line is used.
      With `message_field` set (Fluent Bit's `log`), a cell that isn't JSON is a non-JSON line.
    - Kibana's `-` for missing values and its `.keyword` copies of text fields are dropped.
    - CSV loses value types, so values are converted back using the field's type in the
      registry (int, double, boolean). An empty cell means the field is missing.
    - When the export leaves out columns, the required-field rules aren't applied to the
      missing columns, because those fields may exist but weren't exported. The output names
      the missing columns and suggests exporting all fields. (Kibana 8 exports a `_source`
      column as `-`, so "all fields" is the way to get whole records.)
  - `es`: an Elasticsearch `_search` response, as saved from Kibana Dev Tools or `curl`.
    Records come from `hits.hits[]._source`. The file can hold one response or several
    scroll pages, as a JSON array or one response per line.
  - `jsonl`: one document per line (the bare document, or an object with `_source`), as
    written by `elasticdump` and similar tools.

  Findings refer to the row or hit number instead of the line number, and the Elasticsearch
  `_id` is kept when the export has it. `docs/integration.md` shows how to export a time
  window from Kibana Discover and with `_search`.
- **Records wrapped by Fluent Bit: `[source]`.** Fluent Bit adds its own fields, and often
  keeps the service's line as a string in `log`. With the Kubernetes filter's `Merge_Log On`,
  it puts the fields at the top level, or under `Merge_Log_Key`. A new config section
  handles all three cases:

  ```toml
  [source]
  message_field = "log"            # parse the service's JSON from this field (string or object)
  ignore_fields = ["@timestamp", "kubernetes", "stream", "time", "_p"]   # added by Fluent Bit
  ```

  Fields that Fluent Bit added are then not reported as unknown fields. `--message-field`
  and `--ignore-field` set the same options on the command line.
- **Metrics per service.** A Kibana export usually covers many services, so `check` now
  breaks its result down by `service.name` (or the field set in `service_field`):
  - for each service: the lines, the lines with a violation, a compliance percentage
    (lines without a violation), the violations by rule and the most frequent rule;
  - `--json` gains a `services` key;
  - the text output, the HTML report and the Markdown summary get a "By service" table;
  - `--service NAME` (repeatable) checks only those services;
  - `--metrics FILE` writes the same numbers in Prometheus text format, for a Pushgateway or
    the node_exporter textfile collector. The metric names are `logwarden_lines_total`,
    `logwarden_violations_total` and `logwarden_lines_with_violations_total`, labelled by
    `service`, and by `rule` for violations. `watch` in v0.9.0 will use the same names.

  Lines without a service are grouped as `(none)`. Logged values never appear, only the
  service names.
- **pre-commit hook.** `.pre-commit-hooks.yaml` provides `logwarden-lint-code`, which runs
  `lint-code` on the staged Python, Go, JavaScript/TypeScript and Java files. Semgrep stays out
  of logwarden's dependencies: the hook finds it the way `lint-code` does, on PATH or with uvx.

  ```yaml
  - repo: https://github.com/Ingeniator/logwarden
    rev: v0.8.0
    hooks:
      - id: logwarden-lint-code
  ```

## Breaking changes

None. `--sarif`, `--format`, `[source]`, `--metrics`, the `services` and `input` keys, the
`service` (and, for exports, `id`) key of each finding, and the Action's `sarif` input are
all additions. The text output, the HTML report and the Markdown summary gain a "By service"
table when there is more than one service or a named one (the goldens changed for that and
for the new keys). JSON-lines input is detected as before, so existing commands
behave the same. `configure()` adds the callsite fields only with `callsite=True`. In tests the
pytest plugin turns it on, and the fields are semconv names, so existing checks keep passing.

## Upgrading from v0.7.0

- For PR annotations: add `callsite=True` to `configure()`, then set `sarif: "true"` and
  `security-events: write` in the workflow.
- To analyse production logs: export from Kibana (CSV with all fields, or `_search` JSON), add
  a `[source]` section that matches your Fluent Bit output, and run
  `logwarden check export.csv --html report.html`.
