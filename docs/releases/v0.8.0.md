# logwarden v0.8.0

**Status:** Planned.

Check what services log in production, not only in tests, and show findings on the source line
that logged them.

Until now logwarden saw only what tests and smoke runs exercise. `logwarden watch` reads the
live log stream: the Kafka topic that Fluent Bit or Fluentd already write to, an HTTP endpoint
Fluent can send to, or OTLP. It publishes metrics for Prometheus and Grafana, and writes each
finding as a log line, so findings reach Elasticsearch and Kibana through the same pipeline as
every other log.

## What's new

- **`logwarden watch`: a long-running check of the live log stream.**

  ```bash
  logwarden watch --from kafka://kafka:9092/app-logs     # read the topic Fluent writes to
  logwarden watch --from http://0.0.0.0:8686              # Fluent Bit / Fluentd http output
  logwarden watch --from otlp://0.0.0.0:4318              # OTel SDKs or a Collector
  kubectl logs -f deploy/api | logwarden watch --from -   # anything else, on stdin
  ```

  - **Kafka (the main source).** `watch` joins its own consumer group (`logwarden` by
    default) and starts from the latest offset. It only reads: Fluent, Elasticsearch and
    other consumers aren't affected, and nothing in the pipeline has to change. SASL and TLS
    settings are passed through with `--kafka-option security.protocol=SASL_SSL` and similar.
    The Kafka client is the optional extra `logwarden[kafka]` (confluent-kafka). The core
    install still has no new dependencies, and the Docker image includes the extra.
  - **HTTP.** Accepts JSON lines, or a JSON array of records, as sent by the Fluent Bit
    `http` output (`format json_lines`) and Fluentd `out_http`. This is useful where there is
    no Kafka, such as a local docker-compose, and it needs no extra.
  - **OTLP.** The same receiver as `capture`.
  - **Records that the log pipeline wrapped.** Fluent adds its own fields, and often keeps the
    service's line as a string in `log`. A `[source]` config section, also used by `check`,
    handles that:

    ```toml
    [source]
    message_field = "log"            # parse the service's JSON from this field (string or object)
    ignore_fields = ["@timestamp", "kubernetes", "stream", "time", "tag"]   # added by the pipeline
    ```

    Fields added by the pipeline are then not reported as unknown fields.
  - **Checks in windows.** Lines are collected for `--window` (default 60s) and checked
    together, grouped by service (`service.name`, or the field set in `service_field`).
    Memory is bounded: past `--max-lines` (default 50,000) per window, lines are counted but
    not checked, and `--sample 0.1` checks a fraction of the lines on a busy topic. Throughput
    is measured and stated in the docs.
  - **Outputs.**
    - Prometheus metrics on `--metrics-port` (default 9464):
      `logwarden_lines_total{service}`, `logwarden_violations_total{service,rule}`,
      `logwarden_lines_skipped_total{service}` and `logwarden_source_up`. Labels are bounded:
      rule ids are a fixed list, and services past `--max-services` (default 200) are counted
      as `other`.
    - Findings as JSON lines on stdout, following the standard themselves
      (`event: "logwarden_finding"` with the rule, field, logger, the event that was checked,
      the service and a count). Each finding is written once per window, with a count, so a
      noisy service doesn't flood the pipeline. When `watch` runs in the cluster, Fluent
      ships these lines to Kafka and Elasticsearch like any other container's output. Use
      `--findings-to kafka://kafka:9092/logwarden-findings` to send them to a topic instead.
    - `--snapshot FILE`: rewritten after each window. It uses the same format as `check
      --snapshot`, so `check --compare` and `logwarden catalog` accept it.
    - `--catalog FILE` merges the event names seen in production into the event catalog,
      like `catalog -o`.
    - `/healthz`.
  - Like `check`, findings never contain logged values. `watch` doesn't fail on violations.
    It exits 2 on a bad config. When the source is unreachable it keeps retrying with backoff
    and sets `logwarden_source_up 0`.
  - **Dashboards in the repo.**
    - `integrations/grafana/logwarden.json`: violations by service and rule over time, and
      the top rules and services.
    - `integrations/kibana/logwarden.ndjson`: saved objects for `logwarden_finding` lines
      (findings by service, rule and event, and the latest findings).
    - `integrations/kafka-demo/`: a docker-compose with Kafka, Fluent Bit and `watch`, plus
      Elasticsearch and Kibana in an optional profile. It shows the whole path, and it is
      also how this release is verified.
  - **Checking logs already in Elasticsearch.** `docs/integration.md` shows how to export a
    time window with `_search` and run `check` on it, using `[source]` to unwrap the records.
    This is a documented recipe, not a new command.
- **Findings on the source line: SARIF.**
  - `lint-code --sarif FILE` writes Semgrep's findings as SARIF.
  - `check --sarif FILE` does the same for runtime findings, when log lines say where they were
    logged: `code.file.path`, `code.line.number` and `code.function.name` (semconv 1.45).
    `logwarden.logging.configure(callsite=True)` adds these fields, and the pytest plugin turns
    this on during tests. The Go recipe gets them from slog's `AddSource`. A finding without a
    location is attached to the line in the log file, so it isn't lost. `--source-root`
    removes a path prefix, so locations match the repository.
  - Each SARIF rule links to its section of `docs/rules.md` at this version.
  - The GitHub Action gets a new input, `sarif: "true"` (default `"false"`). It uploads both
    files with `github/codeql-action/upload-sarif`, which needs `security-events: write`. Code
    scanning then shows each finding on the `log.info(...)` line in the PR diff. Code scanning
    is available on public repositories, and on private ones with GitHub Advanced Security.
- **pre-commit hook.** `.pre-commit-hooks.yaml` provides `logwarden-lint-code`, which runs
  `lint-code` on the staged Python, Go, JavaScript/TypeScript and Java files. Semgrep stays out
  of logwarden's dependencies: the hook finds it the way `lint-code` does, on PATH or with uvx.

  ```yaml
  - repo: https://github.com/Ingeniator/logwarden
    rev: v0.8.0
    hooks:
      - id: logwarden-lint-code
  ```
- **Pinned Weaver and semconv versions stay current.** A weekly workflow, `update-pins.yml`,
  looks for new Weaver and semantic-conventions releases. When it finds one, it updates the
  version and its SHA-256, runs the tests, and opens a PR saying what changed. It doesn't
  merge it.

## Breaking changes

None. `watch`, `--sarif`, `[source]` and the Action's `sarif` input are additions.
`configure()` adds the callsite fields only with `callsite=True`. In tests the pytest plugin
turns it on, and the fields are semconv names, so existing checks keep passing.

## Upgrading from v0.7.0

- For production checks: `pip install "logwarden[kafka]"`, or use the image
  `ghcr.io/ingeniator/logwarden:0.8.0`. Run `watch --from kafka://...` with a `[source]`
  section that matches the Fluent output, then import the Grafana or Kibana dashboard.
- For PR annotations: add `callsite=True` to `configure()`, then set `sarif: "true"` and
  `security-events: write` in the workflow.
